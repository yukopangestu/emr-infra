04 · MULTI-TENANCY

One database, isolated per tenant

DATABASE-PER-TENANT

Every clinical tenant receives a dedicated PostgreSQL database, dedicated secret, backup policy, and restore boundary. Shared application services never trust a tenant identifier supplied directly by the client.

01AuthenticateSSO/JWT contains verified tenant identity.
→
02Resolve tenantGateway validates claim or trusted domain.
→
03Fetch routeControl-plane registry returns endpoint + secret reference.
→
04Connect scopedService uses only the resolved tenant connection.
→
05Tenant RDSDedicated PostgreSQL database and backup boundary.
DATA PLANE

Hard data isolation

{{ selected.tenancy.database }}. No cross-tenant tables, shared schemas, or tenant-filter-only authorization for medical records.

CONTROL PLANE

Java Tenant Service + registry

Contains tenant ID, status, RDS endpoint, secret ARN, region, subscription plan, and lifecycle state—but never clinical data.

ACCESS BOUNDARY

Short-lived credential lookup

Services resolve a scoped secret after tenant validation. Credentials are not embedded in JWTs, images, or static configuration.

RECOVERY BOUNDARY

Tenant-scoped restore

{{ selected.tenancy.recovery }}. A restore, export, legal hold, or deletion operation has one tenant as its explicit target.

Java Tenant Service · async provisioningPOST /tenants → 202→Validate slug→Create RDS→Run schema migration→Create secret + KMS grants→Register endpoint→ACTIVE{{ selected.tenancy.provisioning }} · Worker/Step Functions retries safely with idempotency.

Operational trade-off: Database-per-tenant gives the strongest isolation and simple per-tenant restore/export, but increases RDS, proxy, migration, monitoring, and cost-management footprint as tenant count grows.

IN-COUNTRY DR PLANE

Jakarta · separate account / AZs

{{ selected.dr }}. AWS currently has one Region in Indonesia, so the design preserves residency with cross-account vault isolation and a documented regional-outage limitation.

Residency rule: No Singapore or other foreign-region copy for regulated clinical data. Multi-AZ protects against zonal failure; same-region, cross-account backups protect recovery and deletion boundaries but cannot fully protect against a Jakarta regional outage.
