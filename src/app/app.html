04 · MULTI-TENANCY

One database, isolated per tenant

DATABASE-PER-TENANT

Every clinical tenant receives a dedicated PostgreSQL database, dedicated proxy target, dedicated secret, backup policy, and restore boundary. Shared application services never trust a tenant identifier supplied directly by the client.

DATA PLANE

Hard data isolation

{{ selected.tenancy.database }}. No cross-tenant tables, shared schemas, or tenant-filter-only authorization for medical records.

CONTROL PLANE

Java Tenant Service + registry

Contains tenant ID, status, RDS endpoint, proxy endpoint, secret ARN, region, subscription plan, and lifecycle state—but never clinical data.

ACCESS BOUNDARY

User Service RBAC + short-lived credentials

Services resolve a scoped secret after tenant and role validation. Credentials are not embedded in JWTs, images, or static configuration.

RECOVERY BOUNDARY

Tenant-scoped restore

{{ selected.tenancy.recovery }}. A restore, export, legal hold, or deletion operation has one tenant as its explicit target.

Java Tenant Service · async provisioningPOST /tenants → 202→Validate slug→Create RDS + proxy target→Run schema migration→Create secret + KMS grants→Register endpoint→ACTIVE{{ selected.tenancy.provisioning }} · Worker/Step Functions retries safely with idempotency.

Operational trade-off: Database-per-tenant gives the strongest isolation and simple per-tenant restore/export, but increases RDS, proxy, migration, monitoring, and cost-management footprint as tenant count grows.

08 · TENANT PROVISIONING

Async tenant registration sequence

EVENT-DRIVEN · IDEMPOTENT

An administrator receives an immediate acknowledgement while a durable workflow provisions the isolated tenant data plane, creates its subdomain, and waits for TLS validation before activation.

Admin ConsoleOperator
Admin GatewayRBAC + 202
Tenant ServiceControl plane
Provisioning WorkerAsync job
DNS / TLSCloudflare edge
RDS + ProxyPer tenant
01Admin Console→Admin Gateway

POST /tenants with slug, owner and facility metadata

02Admin Gateway→Tenant Service

Validate User Service RBAC, persist request, return 202 + operationId

03Tenant Service→Provisioning Worker

Publish durable TenantProvisionRequested job

04Provisioning Worker→RDS + Proxy

Create dedicated Multi-AZ PostgreSQL, proxy target, schema and KMS-backed secret

05Provisioning Worker→DNS / TLS

Create {{ '{tenant}' }}.jaga.example and certificate validation records

06Provisioning Worker↺DNS / TLS

Poll validation status on a backoff schedule until DNS resolves and TLS is ISSUED

07Provisioning Worker→Audit Log

Record DB_READY · DNS_READY · TLS_READY and every retry/state transition

08Provisioning Worker→Tenant Service

Register proxy endpoint and emit ACTIVE; status is visible to the admin

ASYNC CONTRACT

202 + operation ID

The registration request never waits for infrastructure. The console can poll status or receive an event.

RETRY SAFETY

Idempotent worker

Recorded state lets retries resume without duplicating databases, DNS records, secrets, or certificates.

TLS GATE

Activate only when ready

The tenant is not marked active until the subdomain resolves and its certificate passes validation.
